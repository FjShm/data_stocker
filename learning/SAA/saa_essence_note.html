クロスアカウント・最小権限の黄金パターン
社内エンジニア/他アカウントに必要最小限の権限で作業させたい
→ IAMロール作成 + STS AssumeRole（一時認証情報）
選択肢不正解になる理由
Cognito IDプールエンドユーザー向け認証。社内運用者には設計思想外
共通IAMユーザー監査証跡が取れない（常に不正解）
Admin付与+事後検出事前防止できずリスク大
PowerUserAccess付与自アカウント内の権限強化のみ。他アカウントには無関係
ワイルドカード(*)プリンシパル全世界に公開されてしまう
🧠 覚え方
クロスアカウント問題は「信頼ポリシー（Bが許可）」＋「IAMポリシー（Aがsts:AssumeRole許可）」の2点セットが揃っているかを確認
クロスアカウントでSNSからLambdaを直接トリガーしたい（2つ選択の定番）
→ ① SNS側トピックポリシーでサブスクライブ許可 ＋ ② Lambda側リソースベースポリシーでSNSからのInvoke許可（双方向設定）
組織全体への強制はSCP
全アカウント・ルートユーザー含めてルールを強制したい（例: EBS暗号化必須）
→ デフォルト暗号化（作業側の手間ゼロ）＋ SCP（予防的ガードレール）
  • IAMポリシーだけではルートユーザーの操作を制限できない
  • Config等の事後検出＋自動削除は「一瞬でも違反状態が存在する」ため不正解になりやすい
EC2への安全なアクセス・ログ／マルチアカウント管理
SSHキー/踏み台なしでEC2に安全に接続・ログを残したい
→ Systems Manager Session Manager（SSMエージェント + IAM制御）
複数AWSアカウントへのコンソールアクセスを一元管理したい
→ IAM Identity Center（フェデレーション認証）とSession Managerを組み合わせる
🧠 覚え方
「セッションログを保存したい」も「安全に接続したい」も答えは同じSession Manager。設定画面のポチだけで完結するのが目印。アカウントごとの個別IAMユーザー管理は煩雑化するため不正解になりやすい
KMSカスタマーマネージドキー
Lambda等がカスタマーマネージドキーで復号する権限を与えたい
→ ① IAM実行ロールにkms:Decrypt許可 ＋ ② KMSキーポリシーで実行ロールを許可（2つ選択の定番）
  • SGのアウトバウンド設定は「ネットワーク到達性」の話。IAM認可とは無関係
  • リソースベースポリシーは「外部→Lambda」の方向。「Lambda→KMS」の逆方向には無関係

ポリシー種別アタッチ先
アイデンティティベースポリシーIAMユーザー/グループ/ロールのみ
リソースベースポリシーS3/SQS等の対応リソース側（DynamoDBは非対応）

🧠 覚え方
DynamoDBへのアクセス許可は必ず「実行ロール」経由。「DynamoDBのリソースポリシーで許可」という選択肢は存在しない罠
プライベートコンテンツ配信の使い分け
状況正解
単一のメディアファイル（購入者限定）署名付きURL
複数セグメントファイル群（HLS等）署名付きCookie
S3直接アクセスを防ぎCloudFront経由を強制したいだけOAC（個別の購入判定は不可）
特定オフィス等の固定IPから一括制限WAF IPセット
国単位でのアクセス制限CloudFrontジオリストリクション（追加料金なし）
有料プラン契約者のみAPIアクセスを許可（管理最小）API Gateway 使用量プラン＋APIキー
🧠 覚え方
「単一ファイル→URL」「複数ファイル→Cookie」。OACは経路強制だけで認可判定はしない。API単位の契約者制御はLambdaオーソライザー自作より先に使用量プランを検討
削除禁止要件は Object Lock 一択
ルートユーザーを含め、いかなるユーザーもオブジェクトを削除できない状態にしたい
→ Object Lock「コンプライアンスモード」（ガバナンスモードやバケットポリシーはルート削除を防げない）
  • 初年度アクセスが必要 → S3標準に格納→期間後にライフサイクルでGlacier Deep Archiveへ移行
  • Glacierへの最初からの格納は「即時アクセス不可」でNGになりやすい
  • 既存の大量オブジェクトへの一括適用は個別CLIではなくS3バッチオペレーションを使う
パブリックアクセスの根絶は「予防的コンボ」で
全バケットの公開を一括禁止し、設定変更自体もできないようにしたい
→ S3 Block Public Access（アカウントレベル）＋ SCPでその設定変更操作自体を拒否
  • Config/Macie等の「検出→Lambda等で自動修復」は事後対応（検出的制御）であり、検知までのタイムラグで一瞬公開されるリスクが残る
  • 「制限を解除できないように」という表現は、権限自体を奪うSCPとセットで考える
暗号化の強制 = 予防的制御
アップロード時にサーバーサイド暗号化(SSE)を必須にしたい
→ バケットポリシーで s3:x-amz-server-side-encryption 条件キーを評価しPutObjectを拒否
混同しやすい選択肢実際の意味
aws:SecureTransport転送中暗号化（HTTPS強制）。保存時暗号化とは無関係
s3:x-amz-aclアクセス権限（認可）の制御。暗号化とは無関係
CloudTrail+Lambda自動削除事後検出。一瞬でも非暗号化状態が存在してしまう
RDS/Auroraのダウンタイム最小化シーン別対応表
やりたいこと正解ポイント
メジャーバージョンUP（整合性維持）ブルー/グリーンデプロイ自動バイナリログ同期、1分未満ダウンタイム
フェイルオーバー時の接続断を最小化RDS ProxyアプリのDNSキャッシュ問題を透過的に吸収、コード変更不要
リージョン障害に備えRTO/RPOを最小化Aurora Global Databaseストレージ層レプリケーション、RPO約1秒/RTO約1分
読み取りをスケールしたいAuroraリードレプリカ+リーダーエンドポイント最大15レプリカへ自動分散
よくある不正解パターン（DB系）
  • リードレプリカを昇格させる方式 → 昇格した瞬間に本番との同期が切れる
  • PITR（ポイントインタイムリカバリ） → 復元時点で固定、その後の同期は追従しない
  • DAX → DynamoDB専用。Auroraには技術的に使えない
  • クロスリージョンリードレプリカ（binlogベース） → Global DBよりRTO/RPOが劣る
  • バックアップ復元方式 → 新規作成に数十分、データ損失も発生
  • RDSマルチAZのスタンバイに読取分散 → スタンバイは技術的に読取処理不可
  • DMS継続的レプリケーション → アプリ層同期で遅延・複雑性増（異機種間移行なら正解）
🧠 判断フロー
「ダウンタイム最小×バージョンUP」→ブルーグリーン／「フェイルオーバー×アプリ変更なし」→RDS Proxy／「DR×RTO/RPO最小」→Global DB／「読取スケール」→リードレプリカ
Auto Scaling: 負荷パターンで即判定
負荷の性質正解
予測不能・突発的動的スケーリング（CloudWatchメトリクス/ターゲット追跡）
時刻が事前に確定（始業時等）スケジュールスケーリング
週/日周期があり事前準備（N分前）も必要予測スケーリング（機械学習）＋事前起動設定
🧠 補強（分野4で再登場）
「周期性＋開始◯分前に準備」ときたらターゲット追跡（リアクティブ）では間に合わない。予測スケーリングの事前起動設定が正解
NAT Gatewayは1AZ1個が鉄則
AZ障害が発生しても他のAZのインターネット通信に影響を与えたくない
→ 各AZのパブリックサブネットにNAT GWを1つずつ配置し、同AZのプライベートサブネットから参照
  • 1つのNAT GWに集約 → そのAZ障害で全AZが道連れ（SPOF）
  • NATインスタンスをプライベートサブネットに置く → IGWと通信できず機能しない
  • Egress-Only IGW → IPv6専用のアウトバウンド通信。IPv4のNAT Gatewayに相当する存在
SG・ネットワークアクセス制御
要件正解
特定インスタンスからのみDB接続を許可SGのID相互参照（IPやCIDRではなくSG ID指定）
特定SG以外を拒否したい不可能（SGに拒否ルールは存在しない）
国別にアクセス制限CloudFrontジオリストリクション（追加料金なし）
3層構成のSG設計各層は直前の層のSG IDのみを送信元に許可（応答はステートフルで自動許可）
VPCからS3への閉域アクセスゲートウェイ型VPCエンドポイント（無料・インターネット非経由）
クロスリージョンVPC間の接続制御CIDR指定必須（SG ID参照は同一リージョン限定）
悪意あるIPを即座にブロックNACL（拒否ルール対応。SGは不可）
固定IP＋WAF保護＋低遅延を同時要求Global Accelerator＋ALB＋WAF（CloudFrontは固定IP不可、NLBはWAF不可）
VPCからSQS/SNS等（S3/DynamoDB以外）への閉域接続インターフェイス型VPCエンドポイント（PrivateLink）
サードパーティSaaSへの閉域接続PrivateLink（TGW/VPNは過剰）
🧠 覚え方
SGは「許可のみ」＝ホワイトリスト方式。拒否ルールを求める選択肢は罠。クロスリージョンでは「SG ID参照」ができない点も要注意（IP/CIDR指定に切り替える）
データ取り込み・イベント駆動の定番構成
要件正解
IoT/GPS等のストリームをS3へ蓄積（変換不要）Data Firehose
ファイル受信後すぐに変換処理したいTransfer Family + S3イベント通知 + Lambda
過剰設計になりがちな不正解パターン
  • Glue ETLジョブ → データ変換が不要ならジョブ管理は過剰
  • MSK（Kafka） → クラスター管理の運用負荷が高すぎる（既存Kafka資産があれば正解）
  • EC2+Fluentd等の自前構成 → OS管理・パッチ・監視が発生する時点でほぼ不正解
  • スケジュール実行（15分/1時間ごと） → 「すぐに処理」という即時性要件と矛盾
  • SQS+EC2ワーカー → Lambdaの制限時間(15分)を超える処理や大量バッファリングが必要な場合のみ正解
🧠 覚え方
「サーバー管理ゼロ」×「変換不要」→Data Firehose／「即時イベント駆動」→S3通知+Lambda。管理コンポーネントが増えるほど不正解に近づく
OSで即判定：共有ファイルシステム
接続元OS/要件正解
Linux・複数AZ・複数インスタンス共有EFS（NFS）
Windows Server・AD連携FSx for Windows File Server（SMB）
同一AZ内の高性能クラスタリングのみEBS io2マルチアタッチ
大量の静的ファイル、POSIX互換は不要S3（s3fs-fuseは非推奨扱い）
🧠 覚え方
「NFS」と出たら即EFS。「SMB」と出たら即FSx for Windows。EBSマルチアタッチは"同一AZ限定"が弱点
よくある取り違えの理由
  • EFSをWindowsで使おうとする選択肢 → NFSはWindowsにネイティブ非対応
  • EBSマルチアタッチで複数AZ共有しようとする選択肢 → 同一AZ限定という制約を見落とす
  • S3を「共有ファイルシステム」として使う選択肢 → オブジェクトストレージでPOSIX非互換
  • EC2+Samba/Storage Gatewayでの自前SMB構築 → 運用負荷最小の要件に反する（FSxが正解の定番）
🧠 再確認（分野3で再登場）
「Windows＋SMB＋運用負荷最小」は分野を跨いで繰り返し出る定番パターン。迷わずFSx for Windows File Server
EBS/AMIの性能問題：原因別の正解
状況正解理由
大容量AMIからの起動時にディスクが遅い高速スナップショット復元(FSR)lazy loading（S3遅延読込）を事前初期化で解消
稼働中に単一ボリュームの性能上限に到達複数io1でRAID 0ストライピングOS側で並列化し単一ボリューム限界を突破
🧠 覚え方
「もっと良いボリュームタイプに変える」「容量を増やす」だけの選択肢は根本原因を解決しないひっかけ。EBSの弱点は「初回アクセス」と「単一ボリューム上限」の2種類と覚える
キャッシュ選定：DBの種類で即判定

大容量データ移行：帯域と期限で判定
帯域制限が厳しく期限も短い中で大容量データをS3へ移行したい
→ 実効スループットを計算し、間に合わなければ AWS Snowball（物理輸送）
  • Direct Connectは開通に数週間〜数ヶ月かかり短期の移行には不向き
  • DataSync/Transfer Accelerationは「オンプレ拠点側の物理回線の細さ」自体は解決できない

🧠 覚え方
複数サービスを組み合わせた自前パイプライン（エージェント+Firehose+OpenSearch等）は、標準機能で足りる要件に対しては大抵オーバーエンジニアリングで不正解
S3階層化：アクセスパターンで即判定
アクセスパターン正解
混在・予測不能Intelligent-Tiering（自動階層移動、取得料金なし）
スケジュールが事前に把握できる（低頻度）Glacier Flexible/Deep Archiveへの固定ライフサイクル
長期保管・アクセスほぼなしGlacier Deep Archive（最安）
🧠 覚え方
「数兆件」「混在」「予測できない」というワードが出たら固定ライフサイクルは即除外。Intelligent-Tieringが正解の合図
大容量データ移行：帯域と期限で判定（再確認）
データ量÷回線帯域を計算した結果、期限に間に合わない
→ Snowball / Snowball Edge（オフライン物理転送）
  • Direct Connectは開通に数週間〜数ヶ月、短期案件には非対応
  • Transfer AccelerationはAWS内部通信の高速化のみ。拠点側の回線の細さは解決しない
  • 移行後の保管先は基本 Glacier Deep Archive（最安）を選ぶのがコスト最適化の定石

Savings Plans／イベント駆動処理のコスト最適化
要件正解
EC2とLambdaなど複数コンピュートサービスを横断して割引Compute Savings Plans

  • 常時稼働のBeanstalk/EC2/起動の重いFargateは「軽量・短時間」処理では基本不正解
  • Lambdaと同一リージョンのリソースに接続する場合、同一プライベートサブネットに置くとレイテンシーが最小化される

  • DLM+Lambdaの自前実装、CloudFormation StackSets、DMS常時同期は、いずれも「一元管理・運用コスト最小」の要件では過剰または複雑になり不正解
組織全体のガバナンス自動化
要件正解

不正アクセス・脅威の検出のみ（緩和なし）GuardDuty
OS/ミドルウェアの脆弱性スキャンInspector
🧠 覚え方
GuardDuty/Inspectorは「検出のみ」で自動緩和や遮断はしない。実際に攻撃を止めたいならShield AdvancedかWAFを選ぶ
コンテナ・ファイルシステムの特殊なIAM連携
要件正解
EKSでPod単位のAWS API権限を分離IRSA（OIDCプロバイダー＋サービスアカウントのアノテーション）
EKS内部シークレット(etcd)の暗号化KMSエンベロープ暗号化（組み込み機能）
EMRのジョブ単位アクセス制御＋IMDSブロックEMRランタイムロール
EFSの書き込み・削除をIAMで防止EFSファイルシステムポリシーでelasticfilesystem:ClientWriteをDeny
  • ワーカーノードのインスタンスプロファイルに権限を持たせると全Podで共有されてしまう（IRSAが必要な理由）
  • クライアント側のマウントオプション（-o ro）やPOSIX権限は回避可能。IAM制御はサーバー側（EFS）のポリシーで行う
  • NACLはリンクローカルアドレス(169.254.169.254=IMDS)を通過するため遮断不可。IMDSブロックはEMRランタイムロール等サービス組み込み機能で行う
DB認証情報・暗号化の管理最小化
要件正解
RDS接続情報の安全管理＋自動ローテーションSecrets Manager標準機能（自作Lambda/Step Functionsは不要）
RDSの保存時＋転送時暗号化（管理負荷最小）KMS暗号化＋RDS CA証明書(SSL/TLS)
🧠 覚え方
CloudHSMやVPNなど「追加インフラ・自前改修」が必要な選択肢は「管理負荷最小」の要件と相性が悪く、大抵不正解
