SAA-1003エンジニアの最小権限管理と運用オーバーヘッド削減
◎ 正解
業務内容に応じたIAMロールを作成し、エンジニアが該当ロールを引き受けて作業する
最小特権の原則を満たし、STS（一時認証情報）により長期認証情報の漏洩リスクを低減するベストプラクティス。
✗ Cognito IDプール + グループ機能
Cognitoはアプリのエンドユーザー向け認証。社内エンジニアの運用に使うのは設計思想から外れ運用負荷が激増。
正解化条件自社アプリの一般ユーザーにモバイルからS3等へ一時アクセスを許可したい場合
✗ 共通のIAMユーザーを1つ作成
認証情報の共有は監査証跡ができなくなる重大なアンチパターン。
正解化条件なし（SAA試験では常に不正解）
✗ AdministratorAccess付与+事後検出
管理者権限の一括付与は誤操作を事前に防げずリスクが高すぎる。
正解化条件開発環境の一時検証かつSCPで致命的操作を制限している場合のみ一部正解
⚠ ひっかけキーワード
「運用オーバーヘッドを最小限」に釣られて「共通ユーザー」「Admin一括付与」を選ばない
SAA-1023複数子アカウントDynamoDBから管理アカウントへのセキュアなデータ集約
◎ 正解
子アカウントごとにIAMロール作成（信頼ポリシーで管理アカウント指定）+ STS AssumeRole
長期認証情報を排除し、短時間で自動失効する一時認証情報で最も安全にクロスアカウントアクセスを実現。
✗ リソースベースポリシー + VPCエンドポイント接続
DynamoDBはリソースベースポリシー非対応（経路制限できても認証は解決しない）。
正解化条件S3バケットやSQSキューなど対応サービス間のクロスアカウントアクセスなら正解
✗ Secrets Managerに接続情報を格納・自動ローテーション
DynamoDBはIAM認証であり、格納すべき「シークレット」自体が存在しない。
正解化条件RDSやRedshiftなどパスワード認証が必要なDBへの接続なら正解
✗ IAMユーザー作成+アクセスキー発行+手動ローテーション
長期認証情報を複数管理するアンチパターン。アカウント増加で運用が破綻。
正解化条件なし（SAA試験では常に不正解）
⚠ ひっかけキーワード
「Secrets Manager」の"自動ローテーション"に釣られない。DynamoDBはそもそもパスワード認証ではない
SAA-1027クロスアカウントでのS3バケットアクセス設定
◎ 正解
アカウントBのIAMロールの信頼関係にアカウントAを指定 + アカウントA側でsts:AssumeRoleを許可
長期認証情報を排除し、信頼ポリシー（使われる側）とIAMポリシー（使う側）の両方で制御する標準的なベストプラクティス。
✗ アカウントAのIAMユーザーにPowerUserAccessを付与
自アカウント内の権限が強くなるだけで、別アカウントのリソースへのアクセス権は付与されない。
正解化条件自アカウント内のS3以外のリソースに強い権限を一括付与したい場合
✗ アカウントBにメンバーごとIAMユーザー作成+アクセスキー発行
管理対象ユーザーと漏洩リスクのある長期キーが倍増。運用負荷とセキュリティリスクが激増。
正解化条件なし（SAA試験では常に不正解）
✗ S3バケットポリシーでワイルドカード(*)プリンシパル指定
不特定多数に公開されてしまい重大なセキュリティインシデントになる。
正解化条件静的Webサイトホスティング等で世界中に一般公開したい場合
⚠ ひっかけキーワード
「最小権限の原則」があるため、PowerUserAccessやワイルドカード指定は即除外
LambdaからDynamoDBへの安全なアクセス権限付与
◎ 正解
IAMロールを作成しLambdaの実行ロールに設定
長期認証情報を使わず自動ローテーションされる一時認証情報を使用するベストプラクティス。
✗ LambdaのリソースベースポリシーにPutItem権限を追加
リソースベースポリシーは外部からの呼び出し許可用であり、送信権限の付与には使えない。
正解化条件他アカウントやS3等からこのLambda関数の呼び出し(Invoke)を許可する要件なら正解
✗ DynamoDBのリソースポリシーでLambdaのARNを許可
DynamoDBはリソースベースポリシー自体をサポートしていない。
正解化条件対象サービスがS3やSQS等リソースベースポリシー対応サービスなら正解
✗ Parameter StoreにIAMユーザーのアクセスキーを保存し取得
アクセスキーの使用は長期的な認証情報にあたりセキュリティポリシー違反。
正解化条件IAMロールが利用できないサードパーティ製外部サービスへのAPIキー等を保持する要件なら正解
⚠ ひっかけキーワード
「DynamoDBのリソースポリシー」→DynamoDBはリソースベースポリシー非対応。他サービスへのアクセスは必ず「実行ロール」を使用
IAMアイデンティティベースポリシーの直接アタッチ対象
◎ 正解
IAM ロールおよび IAM グループ（＋IAMユーザー）
アイデンティティベースポリシーはIAMエンティティ（ユーザー・グループ・ロール）にのみ直接アタッチ可能。
⚠ ひっかけキーワード
AWSリソース（RDSやS3等）やOU（組織単位）にはアタッチできない。リソース側は「リソースベースポリシー」、OUへは「SCP」を使用
🧠 このタブの共通鉄則
クロスアカウント・最小権限系の問題は「IAMロール + AssumeRole（STS）」が答えの型。
迷ったら「①長期キーを使ってないか ②信頼ポリシーとIAMポリシーの両方が揃っているか」の2点をチェック。DynamoDBはリソースベースポリシー非対応な点も要注意。
SAA-1004S3とCloudFrontを使用した個別コンテンツの購入者限定配信
◎ 正解
CloudFrontの署名付きURLを購入時にアプリ側で発行し、有効期限付きで返却する
各作品が単一ファイルの場合のプライベートコンテンツ配信で、購入者だけに期間限定アクセスを許可する最適解。
✗ WAFのIPセットルールでIP許可リスト登録
視聴者のIPは動的に変わり管理不能。コンテンツ単位の購入判定もWAF（ネットワーク層）では不可能。
正解化条件特定オフィス等の固定IPからのアクセスを丸ごと一括制限したい場合
✗ オリジンアクセスコントロール（OAC）でS3直接アクセス遮断
OACは「CloudFront経由を強制」するだけで、個別の購入判定は行えない。
正解化条件S3 URL直叩きを防ぎ必ずCloudFront経由にしたい（購入判定は別途）場合
✗ 購入者ごとにIAMユーザー作成+バケットポリシーでGetObject許可
不特定多数へのIAMユーザー発行はスケールせず（上限5,000）、重大なセキュリティリスク。
正解化条件なし（SAA試験では常に不正解）
⚠ ひっかけキーワード
「単一のメディアファイル」→署名付きURLが正解。複数セグメント（HLS等）なら署名付きCookieが正解になるので注意
SAA-1005医療記録の長期保管とルートユーザーを含む削除禁止要件
◎ 正解
S3標準に格納 + Object Lockコンプライアンスモードで保持10年 + 1年後Glacier Deep Archiveへ移行
S3標準で初年度の即時アクセスを担保、コンプライアンスモードでルート含む全ユーザーの削除を完全に防止、Deep Archiveで9年間のコスト最小化。
✗ Glacier Flexible Retrievalに初期格納+バケットポリシーで削除拒否
Glacierは初期格納時に即時アクセス不可。バケットポリシーではルートユーザーの削除を防げない。
正解化条件アクセス頻度が最初から極めて低く、取り出しに時間がかかっても良い場合
✗ S3標準+KMSキーポリシーで削除拒否+Intelligent-Tiering移行
KMSポリシーはオブジェクト削除権限を制御できず、Intelligent-TieringはDeep Archiveよりコスト高。
正解化条件アクセスパターン予測不可能で暗号化キー権限を厳密管理したい（削除防止要件なし）場合
✗ 1ゾーン-IA+ガバナンスモード+Glacier Flexible移行
1ゾーン-IAは単一AZで可用性要件を満たさず、ガバナンスモードは特権ユーザーの削除を許可してしまう。
正解化条件データが再生成可能でAZ耐障害性不要、特定管理者には削除権限を残したい場合
⚠ ひっかけキーワード
「いかなるユーザーも削除できてはならない」→ガバナンスモードやバケットポリシーではルート削除を防げない。必ず「コンプライアンスモード」
SAA-1008S3のサーバーサイド暗号化（SSE）の強制
◎ 正解
バケットポリシーで s3:x-amz-server-side-encryption 条件キーが存在しないPutObjectを拒否
リクエストヘッダーを評価して暗号化されていないアップロードを未然に防ぐ「予防的制御」のベストプラクティス。
✗ CloudTrailで検出しLambdaで自動削除
事後検出・削除の仕組みであり、暗号化されていないオブジェクトが一瞬でも存在してしまうリスクがある。
正解化条件アップロード自体を制限せず、違反オブジェクトに監査ログを残し事後対処したい場合
✗ aws:SecureTransportがfalseの場合にPutObject拒否
これは転送中暗号化（HTTPS通信）の強制であり、保存時暗号化とは無関係。
正解化条件S3への全API通信をHTTPS限定にし平文アクセスを遮断したい場合
✗ s3:x-amz-acl条件キーがauthenticated-readでない場合に拒否
ACLによる認可（アクセス権限）の制限であり、暗号化の有無を評価するものではない。
正解化条件アップロード時に特定の既定ACL付与を強制したい場合
⚠ ひっかけキーワード
「サーバーサイド暗号化」の要件で「転送中暗号化」を意味するSecureTransportと混同しない
S3バケットのパブリックアクセス一括禁止とガードレールの強制
◎ 正解
SCPでs3:PutBucketPublicAccessBlockの変更操作を拒否し、各アカウントでS3 Block Public Accessをアカウントレベルで有効化
設定変更だけで全バケットを一括保護できる「Block Public Access」と、設定変更自体を拒否する「SCP」の組み合わせで、一時的な公開リスクすら発生させない予防的コントロールの最適設計。
✗ CloudWatch監視+SNS通知+手動でCLI修正
変更検知後の手動対応に依存し、夜間・休日の対応遅れでパブリック状態が放置されるリスクがある。
正解化条件自動ブロックが導入できず、人手によるダブルチェックで修正したい場合
✗ Configマネージドルール+SSM Automationで自動修復
問題発生後に直す検出的コントロールであり、検知から修復までのタイムラグの間に一瞬公開されてしまうリスクを排除できない。
正解化条件特定バケットの例外的な公開は許容し、非準拠バケットのみ事後是正したい場合
✗ Macieでスキャン+EventBridge+Lambdaでポリシー自動削除
事後対応の検出的コントロールで公開リスクが残る上、Macieの継続利用料が余計にかかり過剰設計。
正解化条件公開設定だけでなくオブジェクト内の機密データ（PII等）のコンテンツ分析も行いたい場合
⚠ ひっかけキーワード
「制限を解除できないように」＋「運用オーバーヘッド最小」→事後検知系はタイムラグがあり全滅。「Block Public Access＋SCP」の最強コンボ
S3オブジェクトの改ざん防止（WORM機能）と既存オブジェクトへの一括適用
◎ 正解
S3オブジェクトロックをコンプライアンスモードに設定し、既存データへはS3バッチオペレーションで一括適用
ルート含む全ユーザーの削除を遮断し、マネージドで運用負荷なく大量オブジェクトに一括適用できる最適設計。
✗ バージョニング+MFA Delete+ライフサイクルルール
MFA所持者による削除が可能でありWORM（削除禁止）要件を満たさない。
正解化条件削除制限ではなく誤操作復旧と自動削除が目的の場合
✗ コンプライアンスモード+CLIスクリプトで個別適用
個別API実行によるスロットリングやエラー処理の実装負担・運用オーバーヘッドが大きい。
正解化条件対象が数件程度の少数オブジェクトの場合
✗ ガバナンスモード+CLIスクリプトで個別適用
特権権限を持つユーザーによる削除・ロック解除ができてしまい規制要件に不十分。
正解化条件管理者の緊急削除・解除権限を残したい社内標準運用の場合
⚠ ひっかけキーワード
「管理者含め誰にも削除させない」→コンプライアンスモード一択。既存の大量データへの適用は個別CLIではなく「S3バッチオペレーション」
🧠 このタブの共通鉄則
S3の「削除させない」要件はObject Lock コンプライアンスモード一択。
「暗号化を強制」はバケットポリシー + 条件キーで予防的に。転送中(SecureTransport) vs 保存時(SSE)の混同に注意。
「パブリックアクセス根絶」はBlock Public Access + SCPの予防的コンボ。事後検知系（Config/Macie）はタイムラグがあり不正解になりやすい。
SAA-10252つ選択Lambda関数の環境変数暗号化（KMSカスタマーマネージドキー）
◎ 正解（2つ）
① Lambda実行ロールのIAMポリシーにkms:Decryptを許可
② KMSキーポリシーでLambda実行ロールをプリンシパルとしてkms:Decryptを許可
カスタマーマネージドキーの場合、IAMポリシー（使う側）とKMSキーポリシー（使われる側）の両方で許可する「二重認可モデル（AND条件）」が必要。
✗ CloudTrailでKMS APIコールのログ記録を有効化
監査ログ（発見的統制）であり、実行時の復号アクセス権限（予防的統制）を与える設定ではない。
正解化条件KMSの利用状況や復号リクエスト履歴を後から監査したい場合
✗ Lambdaのリソースベースポリシーに KMS サービスプリンシパルからの呼び出しを許可
リソースベースポリシーは「外部サービスがLambdaを呼び出す」方向の制御。「LambdaがKMSを呼ぶ」逆方向とは無関係。
正解化条件S3やEventBridge等をトリガーにLambdaを自動起動させたい場合
✗ VPCセキュリティグループでKMSエンドポイントへのアウトバウンド許可
SGはネットワーク到達性の制御であり、KMS APIの実行認可（IAM）は解決しない。
正解化条件VPC内LambdaがSGのOutbound拒否でKMSと通信できない問題を解消したい（権限は別途付与済み）場合
⚠ ひっかけキーワード
「カスタマーマネージドキー」を見た瞬間、デフォルトキーとは違い「キーポリシー編集必須＝2つ選択」を意識する
SAA-10302つ選択全アカウントでのEBS暗号化の強制と開発者の手順変更最小化
◎ 正解（2つ）
① 各アカウントでEC2のEBSデフォルト暗号化を有効化しKMSキー指定
② ルートOUに適用するSCPでec2:Encryptedがtrueでないec2:CreateVolumeを拒否
デフォルト暗号化で開発者の追加作業をゼロにしつつ、SCPの予防的制御でルートユーザー含む全メンバーの非暗号化ボリューム作成を確実にブロック。
✗ AWS Configマネージドルールで非準拠リソースを自動削除
作成後の発見的制御かつ自動削除であり、一瞬でも非暗号化ボリュームが存在し、重要データが予期せず消失するリスクがある。
正解化条件既存の非暗号化ボリュームを検出し、削除ではなく通知・タグ付けで事後監査したい場合
✗ 各アカウントのIAMユーザー/ロールに個別インラインポリシーを追加
全ユーザー・ロールへの個別設定で運用オーバーヘッドが極めて高く、IAMポリシーではルートユーザーの操作制限を回避できない。
正解化条件Organizations(SCP)未使用で、特定アカウント内の特定IAMユーザー群にのみ暗号化を強制したい場合
⚠ ひっかけキーワード
「手順変更を最小限」→開発者が意識せず暗号化される「デフォルト暗号化」＋組織全体のガードレール「SCP」の組み合わせ
🧠 このタブの共通鉄則
「組織全体で強制」系はSCPが定番の答え。IAMポリシーだけではルートユーザーを制限できない点に注意。
KMSカスタマーマネージドキーはIAMポリシー＋キーポリシーの2点セットを忘れずに。
SAA-1006Session Managerのセッションログ保存と運用負荷の削減
◎ 正解
Session Managerの設定画面からS3への出力を有効化し、保存先バケットを指定する
サービス自体に組み込まれたネイティブ機能を有効化するだけで、追加コンポーネントなしで自動保存できる最善のアプローチ。
✗ Lambda + EventBridgeでセッション終了イベントからログ取得
マネージド機能があるのにカスタムコードの開発・保守が必要になり、バグ混入や運用負荷を高める。
正解化条件サードパーティの外部ストレージ等に、セッション終了を契機にログをカスタム加工して転送したい場合
✗ 各インスタンスでローカル保存+DataSyncで定期転送
大規模移行向けのDataSyncをログ転送に使うのは過剰。バッチ転送中にインスタンスが終了すると未転送ログが消失（コンプライアンス違反）。
正解化条件オンプレ等からTB〜PB級のログファイルを一括・定期同期・移行したい場合
