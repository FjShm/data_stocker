分野1-セキュアなアーキテクチャの設計
Q: SQSへのインターネット非経由（プライベート）接続
◎正解: プライベートサブネットにSQS用インターフェイスVPCエンドポイントを作成しSGを設定 — PrivateLink（ENI）経由でAWS網内で通信を完結。
✗不正解A: ゲートウェイVPCエンドポイントをルートテーブルに追加 — ゲートウェイ型はS3とDynamoDBのみ対応でSQS非対応 / 正解化条件: 接続先サービスがAmazon S3またはAmazon DynamoDBの場合なら正解
✗不正解B: NATゲートウェイを作成しSQSアクセスポリシーでVPC CIDRのみ許可 — NATゲートウェイ経由の通信はパブリックインターネットを経由する / 正解化条件: 外部SaaSなど一般的なインターネット上のパブリックエンドポイントへ送信する要件なら正解
✗不正解C: インターフェイスVPCエンドポイントをパブリックサブネットに作成 — プライベートサブネットからの接続でパブリックサブネットに配置するのは構成として不適切かつ冗長 / 正解化条件: インターフェイスエンドポイントは利用場所（アクセス元EC2と同じプライベートサブネット）に作成する要件なら正解
ひっかけキーワード: 「ゲートウェイ型」と「インターフェイス型」の対応サービス差。S3/DynamoDB以外（SQS等）の閉域接続はすべてインターフェイス型（PrivateLink）。
Q: 低レイテンシー・WAF保護・固定IP要求を満たすマルチリージョンWeb構成
◎正解: Global AcceleratorでエニーキャストIPを取得しALBを登録、ALBにAWS WAFをアタッチ — 2つの静的IPでの単一窓口化、バックボーン経由の低遅延化、L7脅威検知を同時達成。
✗不正解A: Global Accelerator＋NLB＋WAF構成 — NLBはL4ロードバランサーのためAWS WAFの直接関連付けが技術的に不可 / 正解化条件: WAF保護が不要で超高スループット・極小レイテンシーや静的IPが求められる要件なら正解
✗不正解B: NLB＋EIP＋Route 53加重ルーティング＋Shield Advanced構成 — NLBはWAF非対応で加重ルーティングは低遅延化にならず単一固定IPも提供不能 / 正解化条件: トラフィックの割合固定分散とL3/L4 DDoS防御（Shield）に特化した要件なら正解
✗不正解C: CloudFront＋ALB＋WAF＋Route 53レイテンシー構成 — 静的固定IPアドレスを提供できずファイアウォール等のIP許可リスト要件に反する / 正解化条件: クライアント側のIP固定要件がなく静的コンテンツのCDNキャッシュ最適化が主目的の要件なら正解
ひっかけキーワード: 「固定IPアドレスの提供」と「WAF（L7保護）」。CloudFrontは固定IP不可、NLBはWAF不可のため、どちらも満たせる「Global Accelerator + ALB」の組み合わせが正解。
Q: プライベートサブネットから外部APIへのセキュアかつ低運用負荷な接続
◎正解: NAT ゲートウェイをパブリックサブネットに作成しプライベートサブネットのルートに設定 — フルマネージドでインバウンドを遮断しつつ運用負荷最小でアウトバウンド通信を実現。
✗不正解A: NAT インスタンスをパブリックサブネットに起動しソース/デスティネーションチェックを無効化 — OSパッチ適用や高可用性設計などの運用管理負担が発生し不適切 / 正解化条件: 超低コスト優先かつ自前での運用・フェイルオーバー管理を許容する要件なら正解
✗不正解B: インターネットゲートウェイへのルートを追加し Elastic IP を直接割り当て — インターネットからの直接アクセスが可能になりプライベートサブネットの保護要件に反する / 正解化条件: データベースではなくパブリックWebサーバーなどを直接外部公開する要件なら正解
✗不正解C: Site-to-Site VPN を構成しオンプレミスのプロキシサーバー経由で転送 — 不要な迂回経路が発生しオンプレミスインフラへの依存・運用負荷が高く不適切 / 正解化条件: 全通信をオンプレミスのセキュリティ機器でインスペクション（検閲）指定する規制要件なら正解
ひっかけキーワード: 「管理負担を最小限に抑えつつ」→ 自前管理が必要な「NATインスタンス」ではなく、AWSマネージドな「NATゲートウェイ」を選択する。
Q: EKSクラスター内部シークレット（etcd）の暗号化
◎正解: カスタマーマネージドKMSキーを指定しEKSのエンベロープ暗号化を有効化 — 追加管理なしでetcd上のKubernetes Secretを保管時自動暗号化。
✗不正解A: AWS Secrets Managerに格納しExternal Secrets Operatorで参照 — 外部管理には有用だがKubernetes標準のetcd上のSecret自体の暗号化要件を満たさない / 正解化条件: アプリケーションの認証情報をKMS連携で中央一元管理・自動ローテーションする要件なら正解
✗不正解B: EBSボリューム暗号化を有効化してワーカーノードを保護 — EBS暗号化はデータノード用でありAWS管理のコントロールプレーン（etcd）の暗号化には無関係 / 正解化条件: EC2ワーカーノードに一時保存されるローカルデータやログの物理ディスク保護要件なら正解
✗不正解C: HashiCorp VaultをデプロイしS3バックエンドで暗号化 — 独自の外部クラスタ管理が発生し「運用オーバーヘッド最小化」に反する / 正解化条件: AWS非依存のマルチクラウド共通シークレット管理基盤を導入・運用する要件なら正解
ひっかけキーワード: 「Kubernetes クラスター内部のシークレットデータ（etcd）」と「運用オーバーヘッド最小化」。Podから外部シークレットを参照する構成ではなく、EKS組み込み機能である「KMSエンベロープ暗号化」を選択する。
Q: 悪意ある特定IPアドレスからの通信の即座ブロック
◎正解: ALBが配置されたパブリックサブネットのネットワークACLに優先度の高い拒否ルールを追加 — ステートレスで拒否ルールに対応するNACLを用い、ALB到達前に即座遮断する最善手。
✗不正解A: セキュリティグループに特定IPの拒否ルールを追加 — セキュリティグループは許可ルールのみ対応で明示的な拒否（Deny）設定が不可 / 正解化条件: 特定IPからの通信のみを拒否するのではなく、許可対象のIP（ホワイトリスト）のみを指定してアクセス制限する要件なら正解
✗不正解B: バックエンドEC2が配置されたプライベートサブネットのネットワークACLに拒否ルールを追加 — ALBを通過した後の通信は送信元IPがALBのプライベートIPに変換されているためクライアントIP指定の拒否不可 / 正解化条件: クライアントIPではなくALBや特定内部サブネットからの通信自体をネットワークレベルで遮断する要件なら正解
✗不正解C: AWS WAFとCloudFrontディストリビューションを新規作成して前段に配置 — 新規インフラ構築とDNS切り替えを伴うため「即座にブロックする」迅速性に反する / 正解化条件: 即時ブロックではなく、地理的制限や複雑なL7シグネチャによる高度な保護を恒久対策として導入する要件なら正解
ひっかけキーワード: 「即座にブロック」と「セキュリティグループでの拒否」。セキュリティグループに拒否ルールは存在せず、クライアントIPを直接保持しているパブリックサブネット側の「ネットワークACL（NACL）」で拒否ルールを追加する。
Q: クロスアカウントにおけるSNSからLambdaへの直接トリガー設定（2つ選択）
◎正解:
アカウント A の SNS トピックのアクセスポリシーを更新し、アカウント B からのサブスクライブを許可する
アカウント B の Lambda 関数にリソースベースポリシーを付与し、アカウント A の SNS トピックからの呼び出し（lambda:InvokeFunction）を許可する
— クロスアカウント連携では、送信元（SNS側ポリシー）と送信先（Lambdaリソースベースポリシー）の双方向で権限設定を行うことで直接呼び出しが可能になります。
✗不正解A: アカウント A に Step Functions ステートマシンを構築して呼び出す — 不要な中間サービスが入るため構成が過剰で「直接トリガー」の要件に反する / 正解化条件: 複雑なワークフロー分岐やエラー再試行などのオーケストレーションが必要な要件なら正解
✗不正解B: CloudWatch Logs サブスクリプションフィルター経由で検知して起動 — ログを経由させる不要な迂回構成であり、SNSイベントからの直接連携にならない / 正解化条件: ロググループに特定の文字列が出力されたことをトリガーに後続処理を動かす要件なら正解
✗不正解C: アカウント B に Kinesis Data Streams を作成しイベントソースにする — ストリーミング処理用の別構成となり、追加リソースのコストや管理オーバーヘッドが発生する / 正解化条件: 大量データのバッファリングや処理順序の厳格な保証が求められる要件なら正解
ひっかけキーワード: 「クロスアカウントでのSNS→Lambda連携」。同一アカウント内とは異なり、「SNS側のトピックポリシー（サブスクライブ許可）」と「Lambda側のリソースベースポリシー（呼び出し許可）」の両方（双方向）を設定する必要がある点がおさえるべきポイントです。
Q: 3層Webアーキテクチャにおける最小権限のネットワークアクセス制御（【SAA-1144】）
◎正解: ALB のセキュリティグループ ID をソースとしてポート 443 を受け入れるアプリケーションサーバー用セキュリティグループを構成する。そのアプリケーションサーバー用セキュリティグループ ID をソースとしてポート 3306 を受け入れるデータベースサーバー用セキュリティグループを構成する。
— セキュリティグループ（SG）の参照チェーン（連鎖）を利用することで、IPアドレス指定ではなくリソース単位で厳格かつ動的に最小権限のアクセス制御を実現できます。

✗不正解A: 全ての IPv4 アドレス（0.0.0.0/0）からポート 443 のインバウンドを許可…
— プライベートサブネット配置であってもルール上 0.0.0.0/0 を許可することは過剰なアクセスを許すことになり、「最小権限の原則」に反します。
正解化条件: アプリケーションサーバーがALBを介さずインターネットから直接トラフィックを受け取るパブリック配置の構成要件なら正解
✗不正解B: サブネット CIDR からのインバウンドをネットワーク ACL で許可…
— ネットワークACLやCIDR指定による制御はサブネット内のすべてのIPに対して一律許可となり、特定のSGに所属するリソースのみに絞り込むような高精度な制御ができません。
正解化条件: ステートレスなネットワークレベルでの粗いトラフィック遮断（特定サブネット全体の許可・拒否など）を行う要件なら正解
✗不正解C: VPC 全体の CIDR からポート 3306 のインバウンドを許可…
— VPC内の無関係なインスタンスからもデータベースへのアクセスが可能になってしまうため、必要最小限の許可設定になりません。
正解化条件: VPC内部のあらゆるリソースからの DB 接続を制限なく許容する簡易的なデモ・テスト環境構築などの要件なら正解

💡 ひっかけキーワード: 「サブネット CIDR 指定」と「セキュリティグループ ID 参照」
IPアドレス（CIDR）で範囲指定するのではなく、前段の「セキュリティグループ ID」を直接ソース（接続元）に指定することで、Auto Scaling等でIPが動的に変わっても追従し、該当リソースからのアクセスのみをピンポイントで許可できます。
Q: AWS上のサードパーティーSaaSへのインターネット非経由接続（【SAA-1145】）
◎正解: 決済サービスプロバイダーが公開する VPC エンドポイントサービスに対して、AWS PrivateLink 経由のインターフェイス VPC エンドポイントを作成し、AWS 内部ネットワークで通信を完結させる。
— AWS PrivateLink（インターフェイス VPC エンドポイント）を使用することで、パブリックインターネットにトラフィックを晒すことなく、AWS内部ネットワーク（バックボーン）のみを経由して安全かつ最小限の運用負荷でSaaSに接続できます。

✗不正解A: 決済サービスのプロバイダーとの間に AWS Site-to-Site VPN トンネルを構築し、暗号化された通信経路を確保する。
— 通信は暗号化されますがパブリックインターネットを経由する点と、IPsecトンネルの管理など運用負荷が高くなるため要件に不適です。
正解化条件: オンプレミス拠点や自社管理の他拠点とVPC間を暗号化通信で接続する要件なら正解
✗不正解B（選択済み）: AWS Transit Gateway を中央ハブとして配置し、注文処理システムの VPC から決済サービスの VPC へルーティングポリシーを設定する。
— TGWは自社管理の複数VPCやオンプレミスを束ねるための構成であり、サードパーティSaaSとの接続としては構成が過剰かつルーティング管理の運用オーバーヘッドが大きくなります。
正解化条件: 社内の多数のVPCやオンプレミス拠点を中央ハブで集約し、ネットワーク間の双方向ルーティングを一元管理する要件なら正解
✗不正解C: NAT ゲートウェイを VPC に配置し、セキュリティグループで決済サービスの IP アドレス範囲のみへのアウトバウンドを許可する。
— NATゲートウェイ経由の通信はパブリックインターネットを通過するため「インターネットを経由しない」という要件を満たせません。
正解化条件: プライベートサブネットから一般的なインターネット上のパブリックAPIへアウトバウンド通信を行う要件なら正解

💡 ひっかけキーワード: 「AWS上のサードパーティーSaaSへのインターネット非経由接続」
サードパーティのSaaSやAWS提供サービスへインターネットを通さずに閉域接続したい場合は、「PrivateLink（インターフェイスVPCエンドポイント）」一択です。ネットワーク全体を繋ぐTGWやVPNではなく、特定のサービスエンドポイントのみをピンポイントで安全に呼び出すことができます。
Q: 高度なDDoS保護とリアルタイム可視化・自動緩和（【SAA-1146】）
◎正解: AWS Shield Advancedのサブスクリプションを開始し、ALBを保護リソースとして登録する — 実際にトラフィックが通過するリソースでL7 DDoS攻撃のリアルタイム検出と自動緩和を実現。
✗不正解A: GuardDutyを有効化しVPCフローログを自動分析 — 脅威の検出のみでDDoSの自動緩和（防御）機能を持たない / 正解化条件: 悪意のあるアクティビティや不正アクセスの自動検知・アラート通知が目的の要件なら正解
✗不正解B: Inspectorのネットワーク到達可能性分析を実行 — 設定ミスや脆弱性を評価する静的ツールでありリアルタイムのDDoS防御不可 / 正解化条件: EC2インスタンスのOS・ミドルウェアの脆弱性や不要ポートの開放チェックを行う要件なら正解
✗不正解C: Shield Advancedを開始しRoute 53ホストゾーンを登録 — DNSが外部管理のため対象リソースが存在せずALBも保護されない / 正解化条件: AWS上でRoute 53管理のDNSホストゾーンを構築しておりDNSフラッド攻撃を防ぎたい要件なら正解
ひっかけキーワード: 「DNSは外部プロバイダーで管理」。Shield Advanced自体は正解サービスだが、存在しないRoute 53ではなく実際にアプリケーションが受けている「ALB」を保護対象として登録する。
Q: Webアプリ（ALB）へのSQLインジェクション対策（【SAA-1152】）
◎正解: AWS WAF のウェブ ACL に SQL インジェクション検出ルールを含め ALB と関連付ける — マネージドルールにより運用負荷最小で、アプリ到達前にリクエストをインラインでフィルタリング・自動ブロック。
✗不正解A: AWS Shield Advanced を ALB に適用し DDoS レスポンスチームと連携 — 目的がDDoS攻撃の保護・緩和であり、L7のSQLインジェクション検知・遮断には適さない / 正解化条件: 大規模なL3/L4/L7 DDoS攻撃に対する高度な自動緩和や専門チームによる24時間サポートが求められる要件なら正解
✗不正解B: Amazon GuardDuty を有効化し SNS 経由で通知・手動ブロック — 脅威の事後検知・通知サービスであり、リアルタイムな自動遮断ができず運用負荷も大きい / 正解化条件: ネットワークやアカウント内の不正な挙動・侵入の兆候を継続的に検知し、管理者へアラート通知する要件なら正解
✗不正解C: Amazon Inspector で EC2 の脆弱性評価を定期実行しパッチ自動適用 — OS・ミドルウェアの静的な脆弱性スキャンツールであり、実行中の通信（HTTPリクエスト）の検査・遮断不可 / 正解化条件: EC2やECRコンテナイメージ内の既知のOS/パッケージ脆弱性（CVE）を定期スキャン・監査する要件なら正解
ひっかけキーワード: 「SQLインジェクション攻撃の防御」と「最小限の運用オーバーヘッド」。事後検知（GuardDuty）や脆弱性診断（Inspector）ではなく、リクエスト到達前に直接遮断する「AWS WAF（マネージドルール）」を選択する。
Q: 複数アカウントのセキュリティログ統合管理と標準化（【SAA-1153】）
◎正解: Amazon Security Lake を有効化し対象アカウントをソースとして登録する — 開発不要でOCSF規格への自動正規化とS3への一元集約をマネージドで実現。
✗不正解A: AWS Glue ＋ Lake Formation 構成 — ログ変換やOCSF正規化用のETLパイプライン自前開発が必要で運用負荷が大 / 正解化条件: セキュリティ特化ではない一般的な業務データレイクの構築・アクセス制御が目的の要件なら正解
✗不正解B: Kinesis Data Firehose ＋ Redshift ＋ QuickSight 構成 — リアルタイムデータ分析基盤としては有効だが正規化ロジック開発が必要で構成も過剰 / 正解化条件: ログのリアルタイム分析やDWHでの複雑な集計クエリ・BI可視化が主目的の要件なら正解
✗不正解C: CloudWatch Logs ＋ Lambda ＋ OpenSearch 構成 — 各アカウントの設定やLambdaコード開発・OpenSearchの管理運用コストが高い / 正解化条件: ログのリアルタイム全文検索・可視化を独自基盤（OpenSearch）で運用したい要件なら正解
ひっかけキーワード: 「標準化されたスキーマ（OCSF）」と「カスタム開発を最小限に抑える」。自前でのETL処理やデータパイプライン構築を避け、組み込みでOCSF正規化に対応する「Amazon Security Lake」を選択する。
Q: 社内ADと連携した全AWSアカウントへのSSOと一元管理（【SAA-1162】・2つ選択）
◎正解:
AWS Organizations で全機能有効の組織を新規に構成し、部門ごとの AWS アカウントをその組織配下に作成する
AWS IAM Identity Center を組織レベルで有効化し、社内 Active Directory をアイデンティティソースとして接続することでフェデレーションアクセスを構成する
— Organizationsによるマルチアカウント統合を前提基盤とし、IAM Identity Centerで社内ADと連携した一元的なSSO（フェデレーションアクセス）を実現。

Q: グローバル向け認可コンテンツ配信と地理的制限・コスト最適化（【SAA-1166】）

Q: ALBとCognito User Poolの連携認証
◎正解: Cognito User Poolでクライアントシークレット付きアプリクライアントを作成し、ALBリスナールールで認証アクション（authenticate-cognito）を設定 — アプリケーション側での認証コード実装を排除し、ALBレベルでセキュアなユーザー認証を完結
✗不正解A: クライアントシークレットなしのアプリクライアントを作成してALBに設定 — ALB認証連携ではクライアントシークレットが必須条件のため設定エラー（The user pool client must have a client secret）が発生 / 正解化条件: SPAやモバイルアプリなどのパブリッククライアントから直接Cognito Hosted UI等へ接続・認証する場合
✗不正解B: Cognito Identity Pool（インサイトプール）を直接ALBリスナーに連携 — ALBの認証アクションがサポートするのはUser PoolおよびOIDCプロバイダのみでIdentity Poolは直接設定不可 / 正解化条件: 認証後にAWSリソース（S3やDynamoDB等）へアクセスするための仮アクセスキー（STSトークン）を発行する場合
✗不正解C: API GatewayのCognitoオーソライザーをALBの前段に配置 — ALB自体がCognito/OIDC認証機能を保持しているため前段にAPI Gatewayを置くのは冗長でオーバーエンジニアリング / 正解化条件: REST APIの細かな認証・認可制御（スコープ検証やレート制限）をAPIレベルで行う場合
ひっかけキーワード: クライアントシークレット（ALBとCognito User Poolを連携する際の必須設定項目であり、未生成のアプリクライアントは選択不可）
Q: API Gateway＋DynamoDBのミリ秒未満レイテンシ要件
◎正解: DynamoDB Accelerator (DAX) クラスターを導入しAPI Gatewayから参照 — インメモリキャッシュにより読み込みパフォーマンスをマイクロ秒〜ミリ秒未満レベルに高速化
✗不正解A: Elasticache (Redis) を追加構築しAPI Gatewayから直接読み込み — API GatewayとElastiCache間のダイレクト統合機能はなく構成不可 / 正解化条件: Lambda等のバックエンドアプリケーション側でキャッシュ層の複雑なロジック制御を自作管理する場合
✗不正解B: DynamoDBのキャパシティモードをオンデマンドに変更 — オンデマンドは自動スケーリング機能であり、単一クエリのレスポンス時間をミリ秒未満に短縮する効果はない / 正解化条件: トラフィックの予測が不可能で、スループットの自動拡張が必要な場合
✗不正解C: API Gatewayのステージキャッシュを有効化 — TTL（有効期限）内の古いデータが返却される可能性があり、最新データ読み込み要件を満たせない / 正解化条件: データの即時リアルタイム性が不要で、バックエンド全体の負荷軽減のみが目的の場合
ひっかけキーワード: ミリ秒未満の応答時間 / 最新のデータを返却（API Gatewayステージキャッシュによる古いデータ保持リスクを回避し、DAXを選択させる条件）
Q: Aurora / EC2 構成での管理負荷最小化とコスト・高可用性の両立
◎正解: Aurora Serverless v2 + Multi-AZ EC2 (Auto Scaling) — 負荷に応じたシームレスなスケールとマネージドな高可用性を最小運用負荷で実現
✗不正解A: EC2 上に MySQL 自前構築 + マルチ AZ レプリケーション — OS/DB のバックアップ・Failover・パッチ適用等の管理負担が極大 / 正解化条件: AWS マネージドサービスで未対応の特殊な DB カスタマイズやサードパーティ製プラグインが必須な場合
✗不正解B: Aurora Provisioned インスタンス + 静的スケジューリング — 急激な負荷変動に追従できず、アイドル時のリソース浪費によりコスト最適化が困難 / 正解化条件: トラフィックの増減パターンが時間帯単位で完全に予測可能かつ一定な場合
✗不正解C: Amazon RDS for MySQL Single-AZ + 毎時手動スナップショット — AZ 障害時に自動フェイルオーバーが行われず RTO/RPO要件を達成不可 / 正解化条件: 可用性を問わない開発環境かつ最小のベースコストで運用する場合
ひっかけキーワード: 運用オーバーヘッドを最小限に抑える（EC2 自前 DB や Single-AZ の手動運用を排除し、Aurora マネージド機能を選択させる強力な条件）



分野4-コスト最適化されたアーキテクチャの設計
Q: Savings Plansカバレッジ率低下の自動アラート通知（最小運用負荷）
◎正解: AWS Budgetsでカバレッジ予算を作成し閾値アラートを設定 — AWS Budgetsは標準機能でカバレッジ率の閾値監視と通知（メール/SNS等）に対応しており、ノコードで運用負荷が最も少ない。
✗不正解A: Lambda＋CloudWatchカスタムメトリクスで自修復・通知スクリプトを自作 — 独自コード開発や権限・スケジュールの保守が必要でオーバーエンジニアリング / 正解化条件: AWS Budgetsが非対応の独自ロジックによるメトリクス加工や特殊な通知処理が必要な場合
✗不正解B: Cost Explorer＋S3＋QuickSightでダッシュボード化 — 閲覧者が能動的に確認するプル型であり、閾値割れ時の自動アラート（プッシュ通知）を満たせない / 正解化条件: 自動通知ではなく、経営層・チーム向けにビジュアル化したコスト分析ダッシュボードを共有したい場合
✗不正解C: AWS Cost Anomaly Detectionで監視 — 機械学習による急激なコスト変動（異常）の検知用であり、明確な割合（閾値）を指定したカバレッジ率の固定監視は不可 / 正解化条件: アプリのバグや設定ミスによる予期せぬコスト急増・スパイク事故を自動検知したい場合
ひっかけキーワード: 運用負荷を最小限（マネージド機能であるAWS Budgetsで完結するためLambda等の自作はバツ）/ アラート送信（QuickSight等の可視化はプル型のため自動通知要件を満たさない）
Q: 予測不能なトラフィックに対応するDynamoDB構成
◎正解: 標準テーブルクラス＋オンデマンドキャパシティモード — キャパシティ予測が困難なトラフィックに対して自動スケーリングし、読み書き単価も低く抑えられるため最適。
✗不正解A: Standard-IA＋プロビジョニング＋リザーブドキャパシティ — 予測不能なトラフィックに固定コミットは不適切でスロットリングや無駄が発生 / 正解化条件: トラフィックが安定的でアクセス頻度が低いデータを大量保存する場合
✗不正解B: Standard-IA＋オンデマンド — リクエスト単価が標準クラスより約25%高く読み書き多発環境では高コスト化 / 正解化条件: アプリケーションの読み書き頻度が極めて低くストレージ保管コストが支配的な場合
✗不正解C: 標準＋プロビジョニング＋Auto Scaling — 急激なスパイク発生時にスケーリング追従のタイムラグ（数分）でスロットリングが発生 / 正解化条件: トラフィックの変動が緩やかで予測可能かつコスト最優先の場合
ひっかけキーワード: 予測不能（事前予測不可のためプロビジョニングやRIは不可）/ 平常時も一定量の読み書き（リクエスト単価の高いStandard-IAではなく標準クラスが適する）
